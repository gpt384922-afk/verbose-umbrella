# Дизайн Системы Филиальных Ботов

## Цель

Добавить в YC Hunter систему филиалов. Владелец основного бота сможет создавать дополнительные филиалы Telegram-ботов: вводит токен другого бота и Telegram chat ID владельца этого филиала. Каждый владелец филиала работает внутри своего отдельного бота и имеет изолированные аккаунты Yandex Cloud и ханты. Владельцы филиалов не могут создавать филиалы и управлять чужими ботами.

## Выбранный Подход

Используем один процесс приложения, который запускает несколько aiogram-ботов:

- основной бот из `TG_TOKEN`;
- отдельный polling-бот для каждого активного филиала, сохраненного в базе данных.

Так деплой остается простым: один Docker-сервис, одна PostgreSQL-база, один общий слой scheduler/hunter. Филиалы разделяются на уровне данных приложения и проверок доступа.

## Роли И Доступ

Владелец основного бота:

- определяется через `TG_CHAT_ID` или `TG_CHAT_IDS`;
- может пользоваться обычными функциями YC Hunter в основном рабочем пространстве;
- может добавлять, смотреть и отключать филиальные боты;
- является единственной ролью, которой доступно управление филиалами.

Владелец филиала:

- определяется через `owner_chat_id`, сохраненный для конкретного филиала;
- может пользоваться обычными функциями YC Hunter только через своего филиального бота;
- видит только аккаунты и ханты, которые принадлежат его филиалу;
- не видит меню управления филиалами.

Неизвестные пользователи:

- не доходят до обработчиков, как и сейчас в текущем access middleware.

## Модель Данных

Добавляем таблицу `BotBranch`:

- `id`;
- `name`;
- `bot_token`;
- `owner_chat_id`;
- `bot_username`;
- `is_active`;
- timestamps.

Добавляем принадлежность к филиалу для рабочих данных:

- `accounts.branch_id` nullable foreign key на `bot_branches.id`;
- `hunt_jobs.branch_id` nullable foreign key на `bot_branches.id`.

`NULL` означает основное рабочее пространство. Все существующие данные после миграции остаются в основном пространстве, потому что новые поля будут nullable.

Методы репозиториев, которые создают, читают, удаляют аккаунты или работают с хантами, должны принимать branch scope. Branch scope равен `None` для основного бота и ID филиала для филиального бота.

## Архитектура Запуска

Для каждого экземпляра Telegram-бота создается небольшой runtime-объект:

- Telegram `Bot`;
- aiogram `Dispatcher`;
- контекст доступа с branch ID, разрешенными chat ID и флагом `can_manage_branches`;
- общий `AppContext` с той же базой данных, scheduler, state manager, hunter, semaphore и settings.

При старте приложения:

1. Один раз собираем общий application context.
2. Один раз запускаем cleanup.
3. Запускаем polling основного бота.
4. Загружаем активные филиалы из базы данных.
5. Запускаем polling для каждого активного токена филиала.

Когда владелец основного бота добавляет филиал:

1. Бот спрашивает название филиала.
2. Бот спрашивает токен филиального Telegram-бота.
3. Токен проверяется через Telegram `getMe`.
4. Бот спрашивает owner chat ID.
5. Филиал сохраняется в базу данных.
6. Polling для этого филиала запускается сразу, без перезапуска приложения.

Когда филиал отключают:

1. Филиал помечается неактивным в базе данных.
2. Его polling task останавливается, bot session закрывается.
3. Его аккаунты и история хантов остаются в базе данных.

## Интерфейс Бота

В меню основного бота появляется кнопка `Филиалы`. Она показывается только когда текущий bot runtime имеет `can_manage_branches=True`.

Экраны управления филиалами:

- список филиалов с названием, username бота, owner chat ID и активным статусом;
- сценарий добавления филиала;
- экран деталей филиала;
- подтверждение отключения филиала.

Существующие сценарии аккаунтов и хантов визуально остаются такими же. Меняется только источник данных: все запросы идут в рамках текущего branch scope.

Экран активного ханта не должен показывать список облаков со статусами удаления или техническими lifecycle-событиями. Вместо этого он показывает рабочие метрики: статус, время работы, сколько IP перебрано, сколько активных облаков участвует, прогресс по найденным IP, префиксы, ошибку и список найденных IP.

## Поток Данных

Для каждого входящего update middleware добавляет в handler data объект `BotRuntimeScope`:

- `branch_id`;
- `allowed_chat_ids`;
- `can_manage_branches`.

Handlers передают `branch_id` в методы scheduler. Scheduler передает его в репозитории. Репозитории фильтруют данные по филиалу на уровне SQL-запросов.

Примеры:

- список аккаунтов в основном боте: `branch_id is NULL`;
- список аккаунтов в филиальном боте: `branch_id == current_branch_id`;
- владелец филиала запускает хант: новый `hunt_jobs.branch_id` равен ID текущего филиала;
- список активных хантов в филиальном боте: только ханты текущего филиала.

## Обработка Ошибок

Добавление филиала может не пройти, если:

- токен пустой или невалидный;
- токен уже зарегистрирован как активный филиал;
- owner chat ID невалидный;
- polling нового бота не смог стартовать.

Бот должен показать понятную ошибку и сохранить состояние сценария добавления, чтобы владелец основного бота мог исправить значение или отменить действие.

Если polling task одного филиального бота падает, ошибка логируется, runtime удаляется из реестра, но основной бот и остальные филиалы продолжают работать.

## Тесты

Добавляем focused tests для частей, чувствительных к филиалам:

- фильтрация аккаунтов и хантов по branch scope в репозиториях;
- создание и listing аккаунтов через scheduler в рамках филиала;
- access middleware пропускает только owner chat ID конкретного филиала;
- главное меню показывает управление филиалами только runtime основного владельца;
- создание филиала проверяет дубликаты активных bot token.

Ручная проверка:

- запустить приложение с одним основным ботом;
- добавить token филиала и owner chat ID;
- убедиться, что филиальный бот отвечает на `/start`;
- добавить аккаунт через филиальный бот;
- убедиться, что основной workspace и другие филиалы этот аккаунт не показывают;
- запустить хант из филиала и убедиться, что он виден только в этом филиале.
